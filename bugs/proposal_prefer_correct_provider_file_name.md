# PROPOSAL: Require Provider File Name to Match Provider Name

**Status: Open**

Created: 2026-09-02
Type: New rule
Related rules: `prefer_riverpod_provider_suffix`, `prefer_correct_notifier_file_name`

---

## Summary

Flag a file containing a top-level Riverpod provider declaration (`Provider`, `StateProvider`, `FutureProvider`, `NotifierProvider`, `@riverpod`-annotated function, etc.) whose `snake_case` filename doesn't correspond to the provider's own name.

**Closes gap:** DCM `prefer-correct-provider-file-name` (dcm.dev). Implementing this proposal as specified fully closes this competitive gap — see `plans/GAP_ANALYSIS.md` "DCM proper" TRUE GAPS section.

---

## Motivation

Same navigation rationale as `prefer_correct_notifier_file_name`, applied to the provider variable/function itself rather than the notifier class: developers scanning a Riverpod feature directory expect `userRepositoryProvider` to live in `user_repository_provider.dart` (or a file whose stem is the provider name minus the `Provider` suffix). When file names drift from provider names — common after a rename or a copy-paste scaffold — "find references" and manual navigation both degrade. saropa_lints has no rule for this today (confirmed by grep — zero matches for `prefer_correct_provider_file_name` in `lib/src/rules/`), and it is listed as a distinct DCM gap from the notifier file-name rule because top-level provider declarations (not tied to a class) need separate AST handling.

---

## Detection / Behavior

### Should flag (bad code)

```dart
// File: lib/features/user/repository.dart
final userRepositoryProvider = Provider<UserRepository>((ref) { // LINT — expected user_repository_provider.dart
  return UserRepository(ref.watch(apiClientProvider));
});
```

```dart
// File: lib/features/cart/logic.dart
final cartTotalProvider = Provider<double>((ref) { // LINT — expected cart_total_provider.dart
  return ref.watch(cartProvider).items.fold(0.0, (sum, i) => sum + i.price);
});
```

### Should pass (good code)

```dart
// File: lib/features/user/user_repository_provider.dart
final userRepositoryProvider = Provider<UserRepository>((ref) { // OK
  return UserRepository(ref.watch(apiClientProvider));
});
```

```dart
// File: lib/features/cart/cart_total_provider.dart
final cartTotalProvider = Provider<double>((ref) { // OK
  return ref.watch(cartProvider).items.fold(0.0, (sum, i) => sum + i.price);
});
```

## Proposed Tier

Tier: Comprehensive
Justification: Same rationale as `prefer_correct_notifier_file_name` — pure navigation/organization convention, no correctness impact, valuable for teams standardizing Riverpod project layout but not appropriate to gate default builds.

---

## Edge Cases

1. **Multiple providers per file (a common, accepted Riverpod pattern for closely related providers)** — should discuss: DCM's rule targets file-name-to-provider-name correspondence generally, so a reasonable first implementation checks whether at least one provider in the file matches the file's stem, and only flags when NONE of the file's top-level providers match — avoids punishing legitimate multi-provider files while still catching fully-misnamed ones.
2. **`NotifierProvider`/`AsyncNotifierProvider` auto-generated by `@riverpod` code generation on a `build()` top-level function** — the generated provider name (`xProvider`) should be checked against the file stem of the *source* file (not the generated `.g.dart`), since the annotation lives in the hand-written file.
3. **Generated files (`.g.dart`)** — should pass (skip); never hand-named.
4. **Private top-level providers (leading underscore, e.g. `_internalCacheProvider`)** — should pass; private providers are implementation details not meant to be discovered by file navigation, so the naming contract doesn't apply the same way.
5. **Provider declared as a class field or local variable rather than top-level** — should pass; the rule only applies to top-level provider declarations, matching DCM's own scoping.

---

## Alternatives Considered

- **Require exact 1:1 file-to-provider naming, rejecting all multi-provider files** — rejected as too strict; multi-provider files are idiomatic Riverpod for tightly coupled derived providers (e.g. a repository provider plus its mock provider in tests), and DCM's own docs don't forbid this pattern.
- **Merge with `prefer_correct_notifier_file_name` into one rule** — rejected; providers and notifiers are declared with different AST shapes (top-level `VariableDeclaration`/`FunctionDeclaration` vs. `ClassDeclaration`), so keeping them as two rules keeps each visitor simple and keeps diagnostics independently actionable, matching DCM's own two-rule split.
