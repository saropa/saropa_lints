# VS Code extension: turning saropa_lints off does not stop the findings

Reported from: the Saropa Contacts app repo, 2026-10-31.
Type: infrastructure / extension. Severity: high (the user cannot get a quiet, usable editor).

## What the user did to turn it off

1. The extension's "Lint integration" toggle was set Off. It commented out the `plugins: saropa_lints:` block in `analysis_options.yaml` (marker line: `saropa_lints integration turned OFF by the VS Code extension`).
2. `.vscode/settings.json` had `saropaLints.enabled: false` and `saropaLints.scanOnSave.enabled: false`.
3. The user restarted the linter.

## What still happened

- Thousands of saropa_lints warnings and errors stayed in the Problems panel.
- Two `lsp_server.dart` processes from the package snapshot (`.dart_tool/pub/bin/saropa_lints/lsp_server.dart-3.13.7.snapshot`) had been running for about 6 hours and survived the restart.
- Cause found: `.vscode/settings.json` also had `saropaLints.lspServer.enabled: true`. That setting is separate from `saropaLints.enabled`. The master switch `saropaLints.enabled: false` did NOT stop the language server or hide its findings.

## Expected

- `saropaLints.enabled: false` (and the Lint integration Off toggle) stops every saropa_lints source: the analysis plugin, the language server, the scan on save, and the Problems panel entries.
- Or the extension tells the user, in one message, which switches are still on.

## Other places that kept running after the "off" toggle

These are not extension bugs on their own. They show there is no single off switch:

- The pre-commit scan (`dart run saropa_lints scan`) still ran. With the plugin block commented out it exits with code 2 ("No saropa_lints configuration found") and prints "scan could not run", then carries on, so the user sees an error on every commit.
- The CI workflow generated by `saropa_lints:init --emit-ci` has no off switch in its own file and ran on every pull request.
- `saropa_lints:init` regenerates the config block on version sync, so a manual change can be reverted.

## Suggested fix

1. Make `saropaLints.enabled: false` the master switch: it also stops the language server and clears the extension's Problems entries.
2. When the language server is on but the master switch is off, show a single notice naming the setting.
3. After the Lint integration toggle goes Off, make the scan exit 0 with a "disabled" line (not exit 2), so hooks do not report a failure.
4. Document the full list of switches in one place (README: "How to turn saropa_lints completely off").

## Unknowns

- Whether the language server was started by the extension on load or by an earlier session. The process start time was about 9:06 AM and the user restarted the linter later; the same process IDs were still alive.
- Whether `saropaLints.lspServer.enabled` has a default of true or was set by the extension on a tier change. In the user's file the same edit also moved `saropaLints.tier` from recommended to professional.

## Reproduce

1. In a project with saropa_lints active, set `saropaLints.enabled` to false and the Lint integration toggle Off.
2. Leave `saropaLints.lspServer.enabled` true.
3. Reload the window. Check `ps` for `lsp_server.dart` and the Problems panel for saropa_lints entries.

## Done

- Master switch `saropaLints.enabled: false` stops the LSP server, blocks start by setting/command/Restart All, and restarts it when the master switch returns on (suggested items 1 and 2; message is English-only, the owner's translation pipeline must add a catalog key if wanted).
- Suggested item 3: `dart run saropa_lints scan` prints a "disabled" line and exits 0 when the extension's OFF marker is in `analysis_options.yaml` and no `--tier` is given (test: `test/scan/scan_integration_disabled_test.dart`). A project with no config and no marker still exits 2.
- Suggested item 4: README section "How to turn saropa_lints completely off" written.
- Unknown on `lspServer.enabled`: audited. The extension never writes `saropaLints.lspServer.enabled` (tier change writes only `saropaLints.tier`); the value true comes from the `package.json` default (true), so a user's file with it set was set by the user or an earlier session. Not a bug; no change.

## Owner step to close

1. Set `saropaLints.enabled` to `false` and `saropaLints.lspServer.enabled` to `true` in `.vscode/settings.json`, then run "Developer: Reload Window".
2. In a terminal run `ps aux | grep lsp_server.dart`; expect no match other than the grep line itself.
3. Open the Problems panel; expect no saropa_lints entries.
4. Set `saropaLints.enabled` to `true`; confirm `lsp_server.dart` appears in `ps` again and findings return.

Report the result and this bug can be closed.

## Owner decision (2026-10-31)

`dart run saropa_lints scan` exits 0 with a "disabled" line when the plugin block is commented out (answers item 2). README off-switch section and the `lspServer.enabled` default audit (items 3 and 4) are in scope. Item 1 (live VS Code check) stays with the owner.
