# PR 337 — emit-ci, CI engine card, self-linting, and a vibrancy generator fix

## Objective

PR 336 built a composite action that runs saropa_lints on pull requests. It works, but it is undiscoverable: a consumer has to read the CLI guide and hand-copy YAML, and nothing in the product points them at it. This PR closes that gap from both ends — a command that writes the workflow for them, and a control in the extension that turns it on and off — then makes saropa_lints run its own rules against its own code, which it had never done.

One unrelated bug is also fixed here. The Package Vibrancy CI generator produces workflows that always pass. That was found while looking for prior art for the action work, not sought out, and it is separable from everything else in this PR.

These four are what remained of the plan after PR 336. Each is small on its own; together they are the difference between "the action exists" and "a team can actually adopt it."

## What I did

### WP2 — `init --emit-ci` (`lib/src/init/`)

A flag on the existing `init` command that writes `.github/workflows/saropa-lints.yml` into the target project, mirroring the shape and path handling of the `--emit-composite-plugin-scaffold` flag already there.

The generated file opens with a provenance header:

```
# Generated by saropa_lints init --emit-ci
# managed-by: saropa_lints
```

The `managed-by` marker is load-bearing rather than decorative. It is what lets later tooling distinguish "we generated this and it is untouched" from "a human has edited it", which is the difference between a safe regeneration and destroying someone's work.

Unlike the scaffold flag, `--emit-ci` refuses to overwrite an existing file. A workflow governs every contributor's pull requests and frequently carries local customization; losing that to a re-run of a setup command is not a recoverable class of surprise.

The tag is pinned to `@v16.2.1` via a named `ACTION_VERSION` constant. A bare `@v16` would not resolve — the release process creates exact tags only.

I also added the flag to `init --help` and to the CLI guide's flag table. The agent that built this correctly identified the gap and correctly declined to fix it, because `tier_ui.dart` was outside the file boundary it had been given. A flag absent from its own usage text is only half shipped.

### WP3 — CI engine card (`extension/src/systemHealth/`)

A fourth card beside Live Analysis, Scan Daemon and LSP Server, using the same ON/OFF control. New module `ciWorkflow.ts` holds the file logic; `'ci'` joins the engine key union in `engineCardsHtml.ts` and `healthPanel.ts`, with a matching branch in `HealthPanel.onToggle`.

Three decisions carry the design:

**OFF never deletes.** It inserts one marked `if: false` line under the first job. The change is a one-line reversible diff, and any customization the team made to that workflow survives. Delete-and-regenerate would quietly discard their work, and a toggle should not be able to do that.

**Nothing runs git.** Both directions write to the working tree only. The workflow file governs everyone's pull requests, so the change goes through the team's normal review, not a button press.

**The card refuses to imply what it cannot know.** There is no reliable live run status available — the GitHub token is an optional user-pasted setting that is usually empty — so status is derived from the file alone (active, stopped, not-configured) and is never rendered as a passing run. "A workflow file exists" is not "CI passed", and conflating them is the same error as WP0's always-passing workflow. `pid` is omitted; `rssNote` says the work happens on GitHub's runners and cannot be measured locally.

The card's description text states the branch-vs-default-branch divergence outright rather than leaving it as a silent trap: it reflects the file on your current branch, while the default branch's copy is what actually gates pull requests, and the two drift apart routinely.

### WP4 — self-lint job (`.github/workflows/ci.yml`)

The `analyze` job strips `include: package:saropa_lints` and the `plugins:` section from `analysis_options.yaml` before running `dart analyze`, so this repository's own rules have never run against its own pull requests. That step stays — a broken build must not be able to lock its own CI red — so a separate job closes the gap, running the unmodified checkout through the repo's own action via `uses: ./`.

It uses `mode: gate`, which resolves to the `scan` command. That matters twice over: `scan` honors this repo's own `analysis_options.yaml`, so the job runs the rule set the project actually configures; and `scan` writes a human-readable report to stdout, so findings are visible in the log. Non-blocking via `continue-on-error`, since gate mode fails on findings by design. The job reports; it never blocks.

**Correction to the WP4 premise.** The commit message and the original job comment said the `analyze` job's "Strip self-plugin reference" step is why this repo's rules never run on itself. That is wrong: the committed `analysis_options.yaml` carries no `include:` of a tier and no `plugins:` section at all, so that step deletes lines which are not there. The dogfooding gap is real; the reason given for it was not. The job comment now states it accurately.

**What the first run taught.** The job failed on its first CI run with exit 2, `No saropa_lints configuration found`. `scan` reads per-rule configuration from `analysis_options.yaml` and refuses to run without it — precisely the situation above. Passing `tier` fixes it, because `scan_runner.dart:431` returns the tier's rule set before ever consulting the config. `recommended` was chosen because it is the tier the README points consumers at, which makes self-linting the honest comparison.

That failure is also the action's exit-2 handling working as designed: it failed loudly rather than reporting a green job for an analysis that never ran. A version that treated exit 2 as "no findings" would have shown this repo as clean while nothing had been examined.

**What the second run reported.** With a tier supplied, scan completed: 1787 files in 74 seconds, **282 findings in 127 files — 155 error, 127 warning** — at the `recommended` tier. The top rules were `avoid_platform_specific_imports` (39), `require_catch_logging` (31), `avoid_case_sensitive_path_comparison` (21), `avoid_global_state` (17).

Two conclusions followed. First, several of the top rules — `avoid_hardcoded_credentials`, `require_apple_signin_nonce`, `require_isar_id_field` — are almost certainly firing on this repository's own rule fixtures: files written to violate the very rule they test. Counting those makes the number meaningless, so `test/` and the example trees are now excluded and the report covers shipped code.

Second, 155 errors is a backlog, not a regression, and no threshold turns that into a useful gate today. The job now carries `continue-on-error` on the step itself, not merely the job, so the action's exit code can never fail it whatever it finds.

That is deliberate, and it is not the WP0 mistake repeated three files away. The vibrancy generator claimed to gate and silently did not. This job states plainly in its own comment that it reports and never gates, and every finding is in the log for anyone who opens it. `baseline` is the designed answer whenever the team wants to gate on new findings only; committing one is its own decision and its own change.

`fail-on: error` was tried and then removed: with 155 errors present it failed exactly as designed, and keeping a flag that implies a gate on a job that cannot gate would be its own small lie.

### WP0 — Package Vibrancy CI generator (`extension/src/vibrancy/services/ci-generator.ts`)

Two silent defects, both fixed:

1. Thresholds were interpolated into `print()` calls only — no comparison, no non-zero exit. A team that generated this file believed their pull requests were gated on dependency health and they were not.
2. All three platforms invoked `dart run <<'DART_SCRIPT'`. `dart run` does not read a program from stdin, so the checker never executed at all.

The Dart is now written to a real file and run, compares `outdatedCount` against `maxOutdated`, and exits non-zero on breach so the job fails.

`maxAbandoned`, `maxEndOfLife`, `minAverageVibrancy` and `failOnVulnerability` are deliberately **not** enforced. `pub outdated` reports version currency and carries no abandonment, end-of-life, scoring or vulnerability data. Rather than invent a check, the generated script states plainly that these cannot be enforced from this data and points at `saropa_vibrancy_cli`. An honest gap beats a silent lie, and the silent lie is the entire reason this fix exists.

## Considered and rejected

**Adding this to PR 336.** Rejected: 336 is open and awaiting review at a reviewable size. Stacking keeps each PR legible. The cost is that 337 must merge after 336, which is the correct dependency anyway since WP2 and WP3 generate workflows calling that action.

**`mode: annotate` for the self-lint job.** This is what I originally instructed, and it was wrong. In annotate mode the action writes SARIF to a file and passes `--quiet`; with no upload the findings reach nobody, and the job would prove only that the action does not crash — which `action-selftest` already proves. `mode: gate` surfaces a readable report and runs the configured rule set, which is what dogfooding means.

**Uploading the self-lint SARIF to code scanning.** Would give inline annotations on this repo's own pull requests, which is stronger. Rejected as a default because it posts results to the repository's Security tab, and populating a public repository's security dashboard is a deliberate choice for the maintainers rather than something to assume. The job carries a comment explaining exactly how to enable it.

**Deleting the workflow file on OFF.** Rejected: it discards team customization irreversibly. `if: false` is reversible and reviewable. Deletion remains available as an explicit action, distinct from a toggle.

**Deriving a green CI status from file presence.** Rejected outright. It is the same class of error as the WP0 bug being fixed three files away.

**A VS Code setting as the source of truth for the CI toggle.** Rejected: the state genuinely lives in a committed file. A setting would be a second source of truth that drifts from the repository within a day.

**Fabricating a vulnerability check for `failOnVulnerability`.** Rejected for the reason the whole WP0 fix exists.

## Findings a reviewer should know

**A test file that has never run.** `ci-generator.test.ts` was absent from the mocha file list in `extension/package.json`. Nineteen sibling `vibrancy/services/` tests are listed individually; this one was omitted, and no glob catches it. That is how assertions referencing `maxLegacy` — a field `CiThresholds` has never had — survived indefinitely: nothing executed them, so nothing failed. Registered in this PR, which is also what makes WP0's new tests more than decoration.

**A pull request that targets anything but `main` gets no CI at all.** `ci.yml` triggers on `pull_request: branches: [main]`, and `action-selftest.yml` is path-filtered to `action.yml`. This PR was originally opened against `claude/inspiring-pascal-tjfi2j` to stack it on PR 336, and the result was zero check runs — not pending, none. A stacked pull request in this repository is unreviewable by construction, and the Dart changes here would have merged having never been compiled by anything.

Retargeting this PR to `main` fixes it for this case: the branch already contains 336's commits, so `uses: ./` in the self-lint job resolves and CI is complete and correct. The cost is that this PR's diff now includes 336's, making it larger to review. That trade is worth taking over merging code nothing has run.

Worth considering separately whether `ci.yml` should trigger on all pull requests rather than only those targeting `main`. Stacked branches are a normal workflow and silently skipping CI for them is a trap that will catch someone else.

**No CI job runs the extension's TypeScript tests.** `ci.yml` runs the Dart tests, the `saropa_lints_api` package tests, and the Python tier tests. Nothing invokes `npm test`. The entire extension suite is local-only, which is the deeper reason a dead test file went unnoticed. Not fixed here: it is its own change, and switching it on may surface other stale tests that deserve their own attention rather than being swept into this PR.

## What to test

**1. `--emit-ci` writes a usable workflow.** In a scratch Dart project with saropa_lints as a dev dependency, run `dart run saropa_lints:init --emit-ci`. Confirm the file appears at `.github/workflows/saropa-lints.yml`, opens with both provenance lines, and references `@v16.2.1`. Then run it a second time and confirm it refuses rather than overwriting.

**2. `--dry-run` writes nothing.** `--emit-ci --dry-run` should preview and leave the disk untouched.

**3. The generated workflow actually runs.** Push it to a branch on a real project and confirm the job completes. This is the end-to-end check that no amount of local testing substitutes for. Note it will only work once PR 336 is merged and `v16.2.1` contains `action.yml` — until then, point the `uses:` at a branch.

**4. The engine card toggle, in a live VS Code window.** Open System Health, find the CI card. With no workflow present it should read not-configured. Click ON — the file appears in the working tree and the card reads active. Click OFF — the file survives with one `if: false` line added and the card reads stopped. Click ON again — the line goes and the file is back to its original bytes. This was verified programmatically (see below) but not through the actual webview.

**5. The card does not lie about status.** Confirm it never shows a green or passing state purely because the file exists.

**6. The self-lint job.** On this PR, check the `self-lint` job's log: it should show a readable saropa_lints report over this repo's own code, and the job must not turn CI red regardless of what it finds.

**7. The vibrancy generator actually gates.** Run "Generate CI Pipeline" from the Package Vibrancy panel with `maxOutdated` set to 0 in a project that has outdated packages, push the generated workflow, and confirm the job fails. Before this PR it would have passed.

- **The WP3 workflow toggle, compiled and executed against real files.** ON→OFF→ON returns the file byte-identical; both directions are idempotent; every intermediate state parses as valid YAML; a heavily customized workflow keeps its added `cron`, `timeout-minutes`, changed `mode` and added `tier` across the round trip; a file with no recognizable `jobs:` map is left untouched and the call returns false rather than guessing at a structural edit. This is the part the building agent explicitly flagged as untested, and it is the part most able to destroy someone's work.

- WP0's new tests run against both the old and the new generator: 12/12 fail before the fix, 12/12 pass after. A test that passes against broken code would have been worthless here.
- The generated workflows in both WP2 and WP3 reference only inputs that exist in `action.yml`, checked programmatically against its `inputs:` block.
- Provenance header and `managed-by` marker present; no bare `@v16` anywhere.
- `ci.yml` parses, and the `self-lint` job resolves to the inputs intended.
- `scripts/check_doc_links_excluded_paths.py` — passes.

**Did not run:**

- **The engine card in a live VS Code host.** No webview harness available. The file logic beneath it is tested; the UI wiring, the card's rendering, and the toggle round trip through the webview are not.
- **The extension's TypeScript test suite.** It is not wired into CI, and running it locally was not attempted beyond the typecheck.
- **The generated workflows executing on a runner**, for either WP2's output or WP0's three platforms. Their content is verified; their behavior in GitHub Actions or GitLab CI is not.
