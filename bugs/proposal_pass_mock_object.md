# PROPOSAL: Flag Hand-Rolled Fake Objects Passed Where a Generated Mock Belongs

**Status: Open**

Created: 2026-09-02
Type: New rule
Related rules: `no_optional_operators_in_tests`

---

## Summary

Add `pass_mock_object` to flag a test constructing and passing a hand-written fake/stub class (a bespoke subclass or implementation of a dependency's interface with manually hardcoded return values) where the project's standard mocking package (`mockito`/`mocktail`) already generates or provides a proper mock for that type. Duplicated hand-rolled fakes drift out of sync with the real interface silently, since they aren't regenerated when the interface changes.

**Closes gap:** `dart_code_metrics_presets` `pass-mock-object` (pub.dev) and `flutter_skill_lints` `pass_mock_object` (pub.dev) — identical rule shipped under two package names; this proposal covers both. Implementing this proposal as specified fully closes this competitive gap — see `plans/GAP_ANALYSIS.md`.

---

## Motivation

A hand-written fake class implementing a repository/service interface has to be manually kept in sync with every interface change — the compiler won't warn about a fake that silently returns stale/wrong data for a newly added method, because the fake typically hardcodes a `throw UnimplementedError()` or a fixed value rather than tracking real behavior. `mockito`'s generated mocks and `mocktail`'s runtime mocks are both derived from (or checked against) the actual interface, so routing test doubles through them removes an entire class of "the fake lied about the interface" bugs.

---

## Detection / Behavior

### Should flag (bad code)

```dart
class FakeUserRepository implements UserRepository { // LINT — hand-rolled fake where a generated Mock exists
  @override
  Future<User> getUser(String id) async => User(id: id, name: 'Test');
}

test('shows the user name', () async {
  final repo = FakeUserRepository();
  // ...
});
```

### Should pass (good code)

```dart
class MockUserRepository extends Mock implements UserRepository {} // OK — mocktail/mockito-based mock

test('shows the user name', () async {
  final repo = MockUserRepository();
  when(() => repo.getUser(any())).thenAnswer((_) async => User(id: '1', name: 'Test'));
  // ...
});
```

---

## Proposed Tier

Tier: Comprehensive
Justification: package-specific to whichever mocking library (`mockito`/`mocktail`) the project has adopted; requires the project to already have a mocking-package convention to enforce against, so it belongs in an opt-in tier.

---

## Edge Cases

1. **A genuinely simple fake (in-memory `Map`-backed fake repository) used deliberately for integration-style tests rather than unit-level behavior verification** — needs discussion; some teams intentionally prefer real-ish fakes over mocks for this style of test, so a configuration escape hatch may be needed.
2. **Fake class implements an interface that has no corresponding generated mock yet (mock not yet generated by `build_runner`)** — should pass or warn separately; the rule shouldn't force a fake to be deleted before its replacement mock exists.
3. **Fake used only in non-test production code (e.g. a debug/demo mode fake data source)** — should pass; the rule scopes to test files only.
4. **Class named `Fake*`/`Stub*` that actually just extends `Mock` under the hood** — should pass; detection should be structural (does it `extends Mock`/`implements Mock`), not name-based.

---

## Alternatives Considered

- **Ship as two separately named rules matching each source package exactly (`pass-mock-object` and `pass_mock_object`)** — rejected; both are the same detection with only a naming-convention difference between the two source packages, so a single saropa_lints rule avoids shipping a duplicate.
