# Analysis Optimizer

Large VS Code extension projects (e.g. `D:\src\contacts`, ~3,900 Dart files) push the Dart analysis server to 11+ GB RSS, causing crashes; the previously-shipped "balanced memory mode" (v14.5.1) turned out to reduce CPU work only, not RSS, since the analyzer resolves ASTs for every in-scope file before plugin callbacks run. This work adds an Analysis Optimizer dashboard that recommends `analyzer: exclude:` patterns — the only lever available from the extension side to shrink the analyzer's file scope and therefore its memory footprint.

## What changed

**New module — `extension/src/analysisOptimizer/`:**
- `types.ts` — `FileAnalysisMetrics`, `FolderAnalysisCost`, `ExclusionRecommendation`, `AnalysisOptimizerResult`.
- `scanner.ts` — walks workspace `.dart` files via `vscode.workspace.findFiles`, computes regex-based per-file metrics (line/class/function/import counts, widget/async detection, generated-file suffix detection), and derives per-file edit recency from a single `git log --since=<N days>` walk scoped to the last 30 days.
- `scorer.ts` — `computeFileCost` (line/class/function/import-weighted score with a widget multiplier), `aggregateByFolder` (groups by first two path segments, sorted by cost descending), `generateRecommendations` (default high-priority patterns for generated code and build artifacts, plus dynamic folder-based recommendations for folders that are mostly-generated or have no recent git activity; `lib/`, `lib/src/`, and `bin/` are never recommended).
- `analyzerExcludeYaml.ts` — hand-rolled reader/writer for the `analyzer: exclude:` block in `analysis_options.yaml` (mirrors the existing `rulePackYaml.ts` line-scanning approach, no YAML parser dependency). Supports both block-list and inline-array (`exclude: [a, b]`) syntax on read; writer preserves sibling `analyzer:` children (`language:`, `errors:`, etc.) and replaces only the `exclude:` span.
- `analysisOptimizerWebviewProvider.ts` — editor-column webview panel following the `RulePacksWebviewProvider` pattern: header, KPI strip (files in scope, estimated cost, potential savings), current-exclusions list with per-pattern remove, recommendations table with checkboxes and per-row apply, a folder cost heat-map bar chart, and a collapsible "how it works" explainer. Bulk apply (`applyAll`/`applySelected` with >1 pattern) requires a modal confirmation, matching the existing bulk-pack-enable confirmation in `rulePacksWebviewProvider.ts`.

**Three entry points:**
- Sidebar — new leaf row in the Editor Dashboards section (`sectionedSidebar.ts`), positioned before Package Dashboard.
- Critical-memory toast — `processMonitor.ts`'s `showCriticalNotification` gained an "Optimize Analysis" button alongside the existing "Clean Up" / "Don't Show Again".
- Command palette — `saropaLints.openAnalysisOptimizer`, registered in `extension.ts` and `package.json`/`package.nls.json`.

**Corrected a prior release claim:** the v14.5.1 CHANGELOG bullet for balanced memory mode claimed "~7 GB RSS reduction." That was never true — balanced mode skips plugin rule callbacks on unchanged files, which is CPU work; the analyzer resolves ASTs for the full in-scope file set before plugin callbacks run regardless. The bullet was corrected to describe CPU savings only.

## Review findings and fixes

A delegated code review (general-purpose agent, sonnet) surfaced four issues before this shipped, all fixed:

1. **Data-loss bug** — `parseAnalyzerExcludes` did not parse inline-array syntax (`exclude: [a, b]`), returning `[]` for projects using that style. Since `writeAnalyzerExcludes` merges against the parsed existing list, the first apply/remove action would silently drop the user's pre-existing exclusions. Fixed by adding inline-array parsing; the existing block-replacement writer logic already handled the inline case correctly once the reader was fixed.
2. **Accuracy bug** — `queryGitRecency` made two `git log` calls: a `--since`-scoped pass that floored every recently-touched file's recency at `0`, and a second *unscoped* full-history pass whose result could never override that floor (since `days < existing` can never beat `0`). Any file edited 1–30 days ago was reported as edited "today," and the second unscoped walk was pure wasted work on large repos (unbounded history walk with a 10 MB buffer). Fixed by dropping the first call and computing real day-deltas from a single `--since`-scoped walk.
3. **Design-consistency gap** — bulk exclusion apply had no confirmation, unlike the established pattern in `rulePacksWebviewProvider.ts` (`_confirmSdkBulkEnable`) for bulk config writes. Fixed by adding an equivalent modal confirmation (`_confirmBulkApply`) gated on `patterns.length > 1`.
4. **Zero test coverage** on the three new logic modules. Fixed by adding `scorer.test.ts` (10 cases), `analyzerExcludeYaml.test.ts` (13 cases, including regression tests for findings 1 and the inline-array round-trip), and `scanner.test.ts` (5 cases for the pure `computeFileMetrics` function). All 23 pure-logic tests pass via `tsc -p tsconfig.test.json && mocha`.

## Finish Report (2026-08-09) — real-world false-negative and duplicate-write bug

The feature shipped as v14.5.2. Against a real, hand-curated `analysis_options.yaml`, the user reported via screenshot: the optimizer failed to detect exclusion patterns already present in the file (e.g. `**/*.g.dart`, `.dart_tool/**` still showed as "Recommended" with a High-priority badge despite already being excluded), and applying a recommendation produced a duplicate line rather than recognizing the existing entry. They also asked for the "Current exclusions" chip-row UI (called out as dangerous/confusing) to be removed, for "Current exclusions" and "Recommended exclusions" to consolidate into one deduplicated "Exclusions" table, and for sortable table columns.

**Root cause**: the real file's exclude list used entries like `- **/*.g.dart" # Exclude generated files (includes frozen Isar .g.dart – generator re...)` — an unquoted YAML scalar with a stray trailing `"` immediately before an inline `# comment`. Per YAML's own comment rule (a `#` only starts a comment when preceded by whitespace), this parses to the literal value `**/*.g.dart"` (trailing quote included) followed by a comment. The old parser's list-item regex captured the entire remainder including the comment text, and its quote-stripping only handled a balanced leading+trailing quote *pair* — it never matched the clean `**/*.g.dart` pattern the optimizer itself generates, so `isPatternCovered`-style comparisons always failed. `mergeExclusions`'s `Set`-based dedup then treated the dirty existing string and the clean recommended string as two distinct entries, so applying wrote both.

**Fix**:
- `analyzerExcludeYaml.ts` — added `cleanExcludeValue()` (strips an inline comment via a whitespace-then-`#` split, then strips leading/trailing quote characters independently rather than requiring a balanced pair) and `findExcludeLines()`, a single shared line-scanner now used by both the reader and the writer (previously each had its own, subtly different scanning logic). `parseAnalyzerExcludes` dedupes by clean pattern, first occurrence wins. `replaceOrInsertExcludes` looks up each surviving pattern's original raw line via a `rawByPattern` map so an unchanged pattern keeps its original hand-written comment on write; only genuinely new patterns get a plain `- pattern` line.
- `types.ts` / `scorer.ts` — renamed `ExclusionRecommendation` → `ExclusionRow` (added `isApplied: boolean`) and `generateRecommendations` → `buildExclusionRows`. The function no longer hides already-applied patterns; it tags every default-pattern and folder-pattern candidate with `isApplied`, and adds a row for any `currentExclusions` entry that doesn't match a generated candidate at all (a hand-added pattern) so the table can never hide something the file actually excludes. Added `matchExclusionPattern()`, a generic suffix-glob / dir-glob / exact-path matcher, replacing duplicated inline matching logic and reused to size hand-added patterns.
- `analysisOptimizerWebviewProvider.ts` — removed the standalone "Current exclusions" chip section; one `<table id="exclusions-table">` now renders every row with a Status column (Applied / Recommended chip), Apply for recommended rows, Remove for applied rows, and no checkbox on applied rows (bulk-apply only makes sense for not-yet-applied patterns).
- `analysisOptimizerScript.ts` — added click-to-sort on `th.sortable` headers (numeric for files/cost/priority/status, `localeCompare` otherwise), toggling ascending/descending with a visual indicator.
- A follow-up review flagged that the panel re-renders its full HTML from scratch on every Apply/Remove (no partial-DOM-update path exists), which would silently reset the user's chosen sort order each time — surprising given sorting was explicitly requested. Fixed by persisting the sort key/direction via the webview's `vscode.getState()/setState()` API (the contract VS Code actually guarantees survives a `webview.html` reassignment) rather than `localStorage`, and re-applying it on load.

**Testing**: `npx tsc --noEmit` clean. 61/61 mocha tests passing across `scorer.test.js`, `analyzerExcludeYaml.test.js`, `analysisOptimizerScript.test.js` (jsdom-executed), and `overviewTreeFlat.test.js` (sidebar, confirmed unaffected). New regression tests reproduce the exact malformed-YAML shape from the user's file (`**/*.g.dart" # comment`) at both the parser level and the end-to-end write level (asserting the pattern appears exactly once in the written file), plus a two-render persistence test that constructs a second JSDOM instance seeded with the first render's captured `setState` output to prove the sort survives a simulated `webview.html` reassignment.

A second delegated review of this round found no remaining bugs across dedup logic, the shared scanner's edge cases (exclude-as-only-child, empty analyzer block), select-all behavior when every row is applied, and the suffix-regex used for the default pattern list — full findings recorded via the review agent's report during this session, not persisted verbatim here.

## Finish Report (2026-08-09) — YAML alias parse-error bug

The user reported a real Dart analyzer diagnostic against `D:\src\contacts\analysis_options.yaml`: `"Undefined alias."` at a specific line/column, and separately flagged an unrelated `include_file_not_found` error in a `dependency_overrides/*/analysis_options.yaml` (a pre-existing package-resolution issue in that project's `dependency_overrides` setup, unconnected to anything the Analysis Optimizer reads or writes — left untouched).

**Root cause**: YAML reserves a leading `*` on an unquoted scalar for alias-reference syntax (`*anchor_name`, referencing a `&anchor_name` defined elsewhere). Dart glob exclude patterns routinely start with `**` (`**/*.g.dart`, `**/*.bak`, etc.). The writer's fallback path for brand-new patterns emitted them unquoted (`- **/*.g.dart`), and the prior round's "preserve the original raw line so comments survive" fix (from the previous finish report entry above) meant that if an EXISTING entry was already the malformed unquoted form — as several were in the reported file, apparently from careless hand-editing — that exact broken text was preserved verbatim on every subsequent write. Both paths produced or perpetuated genuinely invalid YAML that a real parser rejects, even though this module's own lenient regex-based reader tolerated it fine (explaining why the tool's own detection/dedup logic worked while the actual Dart analyzer failed).

**Fix**: `analyzerExcludeYaml.ts`'s `cleanExcludeValue` was replaced with `splitPatternAndComment`, which returns the pattern and its trailing comment as separate fields rather than folding them into one opaque preserved string. A new `quoteYamlPattern` unconditionally double-quotes every pattern on write (escaping backslash and embedded-quote characters), for both brand-new and previously-existing entries — the write path now reconstructs each line as `- "pattern" # comment` rather than reusing any original raw text. This means a malformed existing entry is silently corrected the next time any exclusion is applied or removed through the dashboard, rather than the parse error persisting indefinitely.

**Testing**: `npx tsc --noEmit` clean, 67/67 mocha tests passing (2 new: one confirming a brand-new `**`-prefixed pattern is written quoted with the unquoted form entirely absent from output, one reproducing the exact malformed real-world entry shape and confirming it gets re-quoted rather than preserved broken). A standalone verification script reproduced the reported file's exact exclude-block shape (multiple unquoted `**/*.xxx"` entries with trailing comments) and confirmed the writer's output contains zero lines matching the unquoted-star pattern after any write.

A delegated review of the fix found no issues: escaping order (backslash-then-quote) doesn't double-escape, no other code depended on the removed `.raw` field, comments are appended outside the quoted pattern (never themselves quoted, so an embedded `"` in a comment is harmless), the read path's quote-stripping is unchanged so round-tripping the new quoted output still detects existing exclusions correctly, and the new tests' `doesNotMatch` assertions are meaningfully scoped (a quoted line's `-` is followed by `"` not `*`, so the negative-assertion regex correctly discriminates the fixed output from the old broken form rather than passing vacuously).

## Finish Report (2026-08-09) — proactive syntax detection and one-click fix

Following the "Undefined alias" quoting fix, a `/finish` reflection gate raised: whether any other code path writes to `analyzer: exclude:` outside `analyzerExcludeYaml.ts` (verified none does — `configWriter.ts`, the only other writer touching `analysis_options.yaml`, only toggles individual `rule_name: true/false` flags and never references `exclude:`), and a brainstormed "whole-file YAML validity sanity-check" feature. The user selected hardening plus the feature; the feature was scoped down from a whole-file check to something narrower and more directly useful: proactive detection specifically for the malformed-exclude-pattern class already fixed, surfaced before the user does anything else.

**What shipped**: `hasMalformedExcludeSyntax(root)` scans the exclude block (both block-list and flow-sequence/inline-array syntax) for any unquoted list item starting with a YAML indicator character, and `fixMalformedExcludeSyntax(root)` re-quotes every existing pattern in place via the existing always-quote write path, without requiring the user to add or remove any specific exclusion first. The webview provider shows a warning banner with a "Fix Syntax" button whenever this is detected — in both the pre-scan empty view and the post-scan result view, computed fresh on every render.

**Two issues found by review and fixed before shipping**:
1. The indicator-character regex (`/^[*&!|>%@\-?:]/`) over-flagged valid patterns. Per YAML's actual rule, `-`, `?`, and `:` are indicators only when followed by whitespace or end-of-value (block-sequence / explicit-key / mapping-value syntax) — a pattern like `-legacy/**` is a perfectly valid unquoted scalar. The over-broad regex would have shown the warning banner and "Fix Syntax" button on files that were never actually broken. Fixed to `/^[*&!|>%@]|^[-?:](\s|$)/`, which only flags the truly unsafe cases.
2. `fixMalformedExcludeSyntax` round-trips through the deduplicating reader, so a file with a genuine duplicate pattern (two raw forms of the same clean pattern, differing only in comment) would silently lose one entry with just a generic success toast — inconsistent with the confirmation modal the existing bulk-apply flow shows for a multi-pattern change. Rather than adding a full confirmation dialog (judged disproportionate for a syntax-repair action), the fix's return type changed from `boolean` to `{ success, duplicatesRemoved }`, and the toast now reads "...and removed N duplicate exclusion pattern(s)" whenever a duplicate was actually collapsed, so the user is told rather than left to notice a missing line later.

A latent-divergence risk was also flagged and fixed cheaply: the flow-sequence detection regex was a second independent copy of the one already used inside the file-scanner, with no shared constant — extracted to `INLINE_EXCLUDE_PATTERN` so the two call sites can't silently drift apart on a future edit.

**Testing**: `npx tsc --noEmit` clean. 77/77 mocha tests passing (10 new: block-list and inline-array malformed detection, negative cases for already-quoted syntax and the false-positive `-`/`?`/`:` regression, missing-file handling, and the duplicate-count reporting behavior). A second delegated review, run after the two fixes, confirmed both were correct by tracing the regex against concrete inputs and the duplicate-count arithmetic against a concrete 3-item/1-unique example, and confirmed by actually executing the test suite (not just reading it) that the new tests exercise the changed `{success, duplicatesRemoved}` return shape rather than a stale boolean comparison — relevant because Node's `assert.strictEqual` types its parameters as `unknown`, so a shape mismatch there would not have been caught by `tsc` alone.

## Finish Report (2026-08-09) — destructive block-rebuild and coverage-detection bugs

A real user reported, against their actual `D:\src\contacts\analysis_options.yaml`, that using the Analysis Optimizer "removed so many items, rearranged file, removed comment, misplaced comments" and called it "very bad" — directly quoted, since the severity warranted it. A `git diff` of the affected file confirmed this in full: standalone section-header comments (`# === Generated Code ===`, `# === Build & Cache ===`, etc.) were gone entirely, blank-line grouping between pattern groups was gone, and every remaining entry had been re-sorted alphabetically, scrambling the file's hand-organized structure. Separately, the user reported the exclusions table still wasn't detecting several already-applied patterns (screenshot showing multiple `dependency_overrides/<package>/**` rows stuck on "Recommended"), and asked for automatic scanning on page load and after every Apply rather than requiring a manual "Scan Workspace" click.

**Root cause of the destruction**: every write action — going back to the very first implementation — rebuilt the entire `exclude:` block from a flat, alphabetically-sorted pattern list (`mergeExclusions` sorts its output), regardless of how small the actual change was. The line-scanner never captured standalone comment-only lines or blank lines in the first place — it only tracked per-pattern trailing comments — so a full rebuild had no way to reproduce them even if it had wanted to. This was true across every prior round of work on this feature (the "preserve comments" fix from an earlier session only preserved a pattern's OWN trailing comment, never section headers or spacing).

**Root cause of the detection gap**: `buildExclusionRows`'s applied-check was exact string-set membership (`appliedSet.has(pattern)`) with no concept of one glob pattern subsuming another. A user's existing `dependency_overrides/**` entry already excludes every subfolder beneath it, but the optimizer's folder-candidate generator produces per-subfolder patterns like `dependency_overrides/flutter_contacts/**`, and that exact string was never itself present in the file — so it perpetually showed as "Recommended", pointing at something that was already fully covered.

**Fixes**:
1. `ExcludeLine` gained a `lineIndex` field (the source line for a block-list item). `replaceOrInsertExcludes` was rewritten around it: the common case (non-empty target list, existing block-list syntax) now computes exactly which lines to delete (patterns no longer wanted, or exact-duplicate lines) and splices them out by index, then appends brand-new pattern lines once at the end — every other line is left byte-for-byte untouched, in its original position, including comments and blank-line grouping. Two edge cases still do a full-block rebuild (wiping to zero patterns; converting from single-line inline-array syntax) since there's nothing structural to lose in either. `fixMalformedExcludeSyntax` was similarly rewritten to walk the raw lines directly and re-quote only the specific lines that are actually malformed, rather than round-tripping through the general writer.
2. New exported `isPatternCovered(pattern, existing)`: true on an exact match, or when an existing `dir/**` entry is a path-prefix of the candidate. `scorer.ts`'s folder-candidate loop now skips (rather than perpetually recommends) a folder pattern already covered by a broader applied exclusion.
3. `analysisOptimizerWebviewProvider.ts`'s `openEditorPanel()` now auto-triggers a full scan on first open; every successful apply/remove/fix-syntax action now triggers a full rescan (previously a cheap re-read of just the exclude list, reusing stale scanned-file data). A review flagged that this could stack concurrent workspace walks if a user clicks several per-row Apply buttons in quick succession — addressed with an in-flight guard (`_scanInFlight`/`_scanQueued`) that coalesces a rescan request arriving mid-scan into a single follow-up scan rather than running two full walks concurrently.

A remaining, documented (not fixed) limitation: a standalone section-header comment isn't tracked as "belonging" to any specific pattern beneath it, so removing the LAST pattern under a header can leave that header orphaned with nothing under it. Still strictly better than the prior behavior, which discarded the header unconditionally on every write regardless of what changed.

**Testing**: `npx tsc --noEmit` clean. 84/84 mocha tests passing. New tests specifically reproduce the reported regression: applying one new pattern against a fixture with section-header comments, blank-line grouping, and hand-ordered entries, asserting the headers, exact blank-line adjacency, and original relative order all survive; a matching test for removal (delete one pattern, assert everything else including its neighbors' exact adjacency is untouched); a test asserting the block is never alphabetically resorted; four `isPatternCovered` unit tests including the exact `dependency_overrides` scenario from the report. One existing test ("re-quotes a malformed unquoted-star entry...") was intentionally rewritten, since its old expectation — that a normal Apply re-quotes unrelated existing malformed entries — is no longer correct behavior by design; only the dedicated Fix Syntax action now touches lines it wasn't explicitly asked to change.

A delegated review focused specifically on the surgical delete/insert index arithmetic (the highest-risk part of the change) hand-traced a non-contiguous multi-delete-plus-insert case and confirmed the descending-order splice with running insertion-point decrement is correct. ## Finish Report (2026-08-09) — pre-write backup safety net

Following the destructive-rewrite fix, a `/finish` reflection gate brainstormed a lightweight recovery mechanism given the trust damage from the prior bug: a local backup snapshot taken before each write, letting a user recover instantly without needing git. The user selected this as the unrequested feature to build, scoped as a minimal, shippable slice (no restore UI — a manual-recovery safety net, not a full undo system).

**What shipped**: `writeAnalyzerExcludes` and `fixMalformedExcludeSyntax` now save the pre-write file content to `analysis_options.yaml.bak` (overwriting any previous backup — a one-step-back snapshot, not a version history) immediately before the actual write. The backup call is wrapped in try/catch and silently swallows failure, since a failed backup must never block the user's actual requested change. Mentioned in the dashboard's collapsed "how it works" hints section.

A refinement was added specifically to avoid degrading the safety net's usefulness: `fixMalformedExcludeSyntax` was changed to skip both the backup and the write entirely when nothing was actually malformed or duplicated — otherwise, clicking "Fix Syntax" on an already-clean file would overwrite a possibly-still-useful backup with a no-op snapshot identical to the current file, silently discarding whatever the PREVIOUS write had backed up.

**One inconsistency found by review and fixed**: the no-op guard was only applied to the block-list branch; the flow-sequence (inline-array, `exclude: [a, b]`) branch still unconditionally wrote and backed up even when nothing needed fixing, directly contradicting the stated rationale for the block-list guard. Fixed by comparing the rewritten inline-array line against its original before deciding whether to write at all.

**Testing**: `npx tsc --noEmit` clean. 89/89 mocha tests passing. New tests confirm the backup contains the true pre-write content (captured before the write call, not derived from post-write state) for both write paths, confirm no backup is created for an already-clean file in BOTH the block-list and inline-array cases, and — combined with the earlier surgical-edit work — a new "realistic sequence" test exercises apply → remove → apply → fix-syntax against a full reconstruction of the originally-reported file's exact section-header/blank-line/malformed-entry shape, asserting every structural element and both applied changes survive the whole sequence.

A delegated review traced backup-before-write ordering across all three write call sites (confirming a backup can never reflect partially-written or already-updated state), confirmed the pre-write content capture is never accidentally aliased to the subsequently-mutated in-memory line array, confirmed a failed backup write can never propagate an exception that blocks the real write, and confirmed the no-op early-return's condition tracking cannot silently skip a genuinely malformed or duplicate line. It flagged the inline-array asymmetry described above (fixed) and separately noted, as an accepted design tradeoff rather than a blocker, that the backup has no restore-button discoverability beyond the collapsed hints panel — reasonable for the requested minimal slice, a candidate for a future round if it comes up again.
