# Live Rule-Count CLI + About Panel Wiring

The rule count shown to users had no single source of truth — it was a hand-typed literal duplicated across ~15 docs/marketing files (`rule_count_correction.md`, same day, fixed the immediate staleness). This follow-on closes the root cause: a generated number instead of a maintained one, surfaced where a user would actually notice it (the extension's About panel), not just a buried CLI command.

## Finish Report (2026-08-19)

**Dart side — `bin/rule_count.dart`:** New CLI, registered as `rule_count` in `pubspec.yaml` `executables:`. Computes counts live from `lib/src/tiers.dart` (`essentialRules`, `getRulesForTier('recommended'|'professional'|'comprehensive'|'pedantic')`, `stylisticRules`, `getAllDefinedRules()`) — the exact sets the plugin itself uses, so the number cannot drift from what actually ships. Supports `--format text` (default) and `--format json`. Verified by running both modes directly: text and JSON output matched the tier-distribution figures from the prior correction (essential 331, recommended 1036, professional 1881, comprehensive 2094, pedantic 2109, stylistic 223, total 2332).

**Extension side:**
- `extension/src/views/ruleCountCliRunner.ts` — new module, `fetchRuleCounts(projectRoot)`, cloned spawn pattern from `projectVibrancyCliRunner.ts` (Windows `shell:true` for `.bat`/CVE-2024-27980, `resolveCliCwd` for dev-vs-production CLI resolution). Simpler than the vibrancy runner: no streaming/progress/control-file support, since a set-count is sub-second and buffered stdout collection is sufficient. 10s timeout kills the child and resolves `null` rather than hanging the panel.
- `extension/src/views/aboutView.ts` — `showAboutPanel` is now `async`; opens the panel immediately with static content (no wait on a Dart spawn), then swaps in the live count once `fetchRuleCounts` resolves (or leaves the panel as-is if no workspace is open or the CLI call fails — best-effort, no error surfaced for a supplementary figure). New `buildRuleCountBlock` renders a strip above the markdown body via a new `en.json` key `about.ruleCountStrip` (interpolated placeholders for all 7 counts, not string concatenation, per the project's i18n rules).
- `extension/src/extension.ts` — the `saropaLints.showAbout` command registration updated to `void showAboutPanel(...)` since the function became async.

**Verification:** `npx tsc --noEmit -p extension` — clean, no errors. `dart run bin/rule_count.dart` and `--format json` — both verified against the known-correct counts. No UI screenshot verification was performed (no VS Code Extension Development Host was launched in this session) — the panel's rendering, the loading→loaded swap, and the fallback-when-CLI-fails path are unverified at the pixel/behavior level, only at the type/logic level.

**Translation status:** The new `about.ruleCountStrip` key was added to `en.json` only. The user asked to run the translation regen (`generate_translations.py`); the script's interactive mode-selection prompt (`[1/2/3/4/a]`) could not be answered non-interactively — piping input to it was blocked by the permission classifier — so the regen did not complete. The command was handed to the user to run themselves and choose mode `1` (close gaps only). Until then, non-English users see the English string for this one key (the runtime's `l10n()` falls back to English on a missing key, so this degrades gracefully rather than breaking).

**Versioning:** `pubspec.yaml` bumped to `15.1.3` (from `15.1.2`, which the user had already deployed via a separate concurrent publish run during this session). `extension/package.json`'s version was deliberately left unbumped — the observed convention in this repo is that the publish/release script syncs it to match `pubspec.yaml` at release time, not during feature development.

**Not done / explicitly out of scope for this slice:** no status-bar surfacing of the rule count (only the About panel) — kept the slice minimal per the /finish reflection-gate instruction ("minimal, shippable slice"); the status bar's tooltip rebuilds on every scan/save, so wiring a Dart spawn into that hot path would need debouncing/caching that didn't fit this slice.
