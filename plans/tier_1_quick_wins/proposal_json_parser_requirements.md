# PROPOSAL: Require Matching toJson/fromJson Pair on JSON-Serializable Classes

**Status: Open**

Created: 2026-09-02
Type: New rule
Related rules: `missing_field_in_equatable_props`

---

## Summary

Add `json_parser_requirements` to flag a class that defines one half of the JSON serialization contract (`toJson()` instance method or `fromJson(Map<String, dynamic>)` factory/static constructor) without the other. A class meant to round-trip through JSON needs both directions, or callers silently lose the ability to serialize or deserialize it.

**Closes gap:** `json_parser_linter` `json_parser_requirements` (pub.dev). Implementing this proposal as specified fully closes this competitive gap — see `plans/GAP_ANALYSIS.md`.

---

## Motivation

A class with `toJson()` but no `fromJson` factory (or vice versa) is usually an incomplete migration — someone added serialization for one direction (e.g. sending analytics events) and never finished the read path, or a `fromJson` factory was hand-written but `toJson()` was forgotten, breaking persistence/caching that relies on round-tripping. Flagging the asymmetry at the class definition catches it before a caller discovers the gap at runtime.

---

## Detection / Behavior

Flag a class declaration that has exactly one of: an instance method named `toJson` returning `Map<String, dynamic>` (or similar), or a `factory ClassName.fromJson(Map<String, dynamic> json)` / static `fromJson` constructor — but not both.

### Should flag (bad code)

```dart
class UserProfile {
  final String name;
  UserProfile(this.name);

  Map<String, dynamic> toJson() => {'name': name}; // LINT — no fromJson factory to reverse this
}
```

### Should pass (good code)

```dart
class UserProfile {
  final String name;
  UserProfile(this.name);

  Map<String, dynamic> toJson() => {'name': name}; // OK

  factory UserProfile.fromJson(Map<String, dynamic> json) =>
      UserProfile(json['name'] as String); // OK — round-trip complete
}
```

---

## Proposed Tier

Tier: Recommended
Justification: Catches a common half-finished-migration bug with a clear fix and no legitimate reason for the asymmetry in the common case.

---

## Edge Cases

1. **Class extends/mixes in a base that already provides the missing half** — should pass; check the full inheritance chain, not just the declaring class, before flagging.
2. **`toJson`/`fromJson` generated by `json_serializable` (`@JsonSerializable()` + part file)** — should pass; both halves exist in the generated `.g.dart` part, so resolve across part files rather than the single source file.
3. **Write-only DTO intentionally lacking `fromJson` (e.g. outbound analytics event)** — needs discussion; likely needs an opt-out annotation (`@JsonWriteOnly` or similar) rather than a blanket exemption, to avoid silently missing genuine gaps.
4. **`fromJson` present as a plain named constructor instead of `factory`** — should still be recognized as satisfying the pairing.

---

## Alternatives Considered

- **Require the pairing only when a `@JsonSerializable`-style annotation is present** — rejected as too narrow; the bug this rule targets is most common in hand-written serialization code that never uses codegen annotations.
