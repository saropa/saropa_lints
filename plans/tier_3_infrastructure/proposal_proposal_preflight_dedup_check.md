# PROPOSAL: Pre-flight Conceptual Duplicate Check for New Rule Proposals

**Status: Open**

Created: 2026-09-06
Type: Tooling / process
Related: `plans/tier_1_quick_wins/duplicate_manifest.json`, `scripts/check_rule_name.py`,
`scripts/modules/_duplicated_messages.py`

---

## Summary

Add a pre-flight check, run before a new rule proposal is written (or immediately after, before
implementation starts), that searches existing `LintCode` names, lint messages, DartDoc, and class
names under `lib/src/rules/` for both exact-name collisions and conceptual overlap with the new
proposal's subject. This closes the gap that let `avoid_any_version` get proposed, written up, and
left open as a duplicate of the already-shipped `avoid_unbounded_dependency` — same concept
(unpinned/unbounded version constraints), different name, so the existing name/alias-only dedup
scan (`duplicate_manifest.json`) never flagged it.

---

## Motivation

`duplicate_manifest.json` is generated by matching a proposal's `rule_name` (and any
`configAlias`/alias) against `tiers.dart`, `saropa_lints.dart`, and rule source files. That catches
exact and aliased name collisions but has no notion of "these two rules do the same thing under
different names." `avoid_any_version` (proposed: flag `any` version constraints in `pubspec.yaml`)
is a strict subset of the shipped `avoid_unbounded_dependency` (flags unbounded/unpinned
constraints generally, `any` included) — conceptually redundant, but the manifest scored it `new`
because no name or alias matched.

Authoring a proposal, writing DartDoc/Bad/Good examples, and only discovering the overlap at
implementation or review time wastes the same cycle `check_rule_name.py` was built to save for
core-lint-name collisions (see that script's own docstring: three same-mistake catches in three
days). The fix is the same shape: a cheap, explicit check run **before** the proposal is written,
not a smarter automated scanner (conceptual similarity is not reliably automatable — see
Alternatives Considered).

---

## Detection / Behavior

Two complementary components:

### 1. `scripts/check_proposal_overlap.py` (new script)

```
python scripts/check_proposal_overlap.py "<keyword> <keyword> ..."
```

- Takes one or more keywords/phrases drawn from the *concept* of the new proposal (not just the
  proposed rule name) — e.g. for `avoid_any_version`: `version constraint`, `any`, `unbounded`,
  `pubspec`.
- Greps (case-insensitive) `lib/src/rules/**/*.dart` for each keyword against:
  - `LintCode` name arguments
  - `problemMessage` / `correctionMessage` string literals
  - class-level DartDoc comments (the `///` block immediately above each rule class)
  - class names themselves
- Prints every rule file with at least one hit, grouped by rule, so the author can eyeball
  candidates for conceptual overlap — this is a recall tool (cast wide, human judges), not a
  pass/fail gate. No exit-code failure; unlike `check_rule_name.py`'s exact-match collision (which
  is unambiguous), overlap is a judgment call and should never silently block authoring.
- Exit code stays 0 always; output is advisory.

### 2. Proposal template checklist step

Add a step to the proposal-authoring instructions (`CLAUDE.md` "Adding a New Lint Rule" step 0,
alongside the existing `check_rule_name.py` call) and to the proposal template's front matter:

```
0a. Run `python scripts/check_proposal_overlap.py "<concept keywords>"` and review every hit.
    If an existing rule covers the same concept, note it under a new "Overlap Check" section
    in the proposal (below) instead of writing "Related rules: none".
```

Add a mandatory `## Overlap Check` section to new proposals (between `Motivation` and
`Detection / Behavior`, matching the position `Related rules:` already occupies in the front
matter of e.g. `proposal_avoid_dependency_overrides.md`):

```markdown
## Overlap Check

- Keywords searched: <list>
- Candidates reviewed: <rule names, or "none found">
- Conclusion: <e.g. "No conceptual overlap" | "Overlaps with X — see Related rules above">
```

## Edge Cases

1. **Keyword too generic** (e.g. "async", "widget") — floods output with irrelevant hits. Script
   should print a hit-count warning ("N matches across M files — consider narrower keywords") but
   still show results; the author decides.
2. **Concept genuinely has zero prior art** — script reports no hits; proposal's Overlap Check
   section records "none found" and authoring proceeds normally.
3. **Overlap found but the new rule is a deliberate narrower/stricter variant** — not a duplicate;
   Overlap Check section should say so explicitly and cross-reference, same as
   `proposal_avoid_dependency_overrides.md` already does via its `Related rules:` line.
4. **DartDoc references the concept only in passing** (e.g. mentions "version" in an unrelated
   example) — false positive; acceptable since this is a recall/advisory tool, not a gate.

---

## Alternatives Considered

- **Fully automated conceptual-duplicate detection (embeddings/semantic similarity over proposal
  Summary vs. existing rule DartDoc)** — rejected for this proposal's scope. Higher build cost, no
  existing embedding infrastructure in the repo's Python tooling, and a wrong "no overlap" verdict
  from an automated semantic scorer is worse than today's baseline because it would look
  authoritative. A keyword-grep-and-human-review tool is cheap, transparent, and matches the
  project's existing pattern (`check_rule_name.py` is also a simple exact-match check backed by
  human judgment for the ambiguous cases it flags).
- **Extend `duplicate_manifest.json` generation to also do keyword matching automatically for every
  proposal in bulk** — useful as a periodic audit, but doesn't solve the write-time problem: the
  manifest is generated after a batch of proposals already exists. A pre-flight script the author
  runs while drafting is what actually prevents the `avoid_any_version` scenario (proposal written,
  reviewed, and left open before anyone re-ran the batch scan).
- **Rely on reviewer memory / manual `grep` at review time** — status quo; already failed once.

## Implementation Notes

- `check_proposal_overlap.py` can share the `CORE_DART_LINT_NAMES`-style `sys.path` setup pattern
  used by `check_rule_name.py` if it needs to import shared utilities from `scripts/modules/`, but
  needs no such import itself — it's a standalone grep over `lib/src/rules/`.
- Reuse the DartDoc/class-scanning approach already present in
  `scripts/modules/_duplicated_messages.py` (`extract_message_strings`, file walk skipping
  `all_rules.dart`) rather than re-implementing regex extraction from scratch.
- Not wired into `publish.py` or any CI gate — this is a write-time author aid, not a publish-time
  block, since "conceptual overlap" is not a mechanically-decidable pass/fail condition.
